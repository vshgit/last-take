# Разработка и сборка

## Среда

- Игровой движок: Godot 4.5.1 в исходной сборке. Повторная проверка восстановления использует установленный Godot 4.6.3, Linux.
- Язык: GDScript; графические эффекты — Godot shader language.
- Редактируемый персонаж: `ArtSource/character-v10/cinemaniac_v10.blend`; для его изменения нужен Blender. Готовые GLB уже в `Source/assets/`, Blender не нужен для обычного запуска игры.
- Существующие Python-генераторы используют Pillow/NumPy, отдельные скрипты — Blender и локальный Piper/ONNX. Точные импорты и внешние пути смотреть в конкретном скрипте. Эти зависимости не нужны для запуска готового проекта.
- Речь уже сгенерирована. Модель Piper ru_RU-denis-medium и внешние инструменты не считаются включёнными, пока не найдены отдельно. Не обещать полную воспроизводимость генерации голосов из одного репозитория.

## Проверки

Команды из корня репозитория (в Windows имя/путь исполняемого Godot может отличаться):

```sh
python3 tools/verify_recovery.py
godot --headless --editor --path Source --import
godot --headless --path Source --audio-driver Dummy -- --qa
```

Дождаться завершения импорта перед запуском QA. Игровая проверка должна завершиться и показать все шесть маркеров: `V1_CHECKS_PASSED`, `SOUNDS_CHECKS_PASSED`, `GESTURE_REPLAYS_PASSED`, `GESTURE_INPUT_CHECKS_PASSED`, `V09_CHECKS_PASSED`, `GAMEPLAY_CHECKS_PASSED`. Точные имена сверять с текущими исходниками; в отчёте фиксировать реальные найденные маркеры. Проверять также `SCRIPT ERROR`, `Assertion failed`, ошибки загрузки и exit code. Тайм-аут не считать успехом.

Исторические проверки 0.10 входят в общий QA вместе с 1.0. Headless-проверки не оценивают внешний вид, удобство управления и слышимость на реальном устройстве. Для затронутых игровых изменений нужна ручная проверка. Сообщения освобождения ресурсов при выходе перечислять отдельно.

`tools/verify_recovery.py` проверяет побайтовую сохранность исходного состояния; после намеренных игровых правок расхождения с базой ожидаемы и не являются автоматическим основанием откатить правку. Историю сохраняет Git; старый манифест не переписывать под новое поведение.

## Экспорт Windows

Установить соответствующие версии движка и export templates. В `Source/export_presets.cfg` сохранён профиль `Windows Desktop` с x86_64 и встроенным PCK. Стандартный путь в старом профиле — `../LastTake.exe`; лучше задавать отдельный каталог сборки явно:

```sh
mkdir -p builds
godot --headless --path Source --export-release "Windows Desktop" ../builds/LastTake.exe
```

Проверить фактический выходной путь. Рядом с EXE можно разместить `Launch-Compatibility.cmd` из корня и сведения о версии. Нативно запустить на Windows, проверить вступление, четыре типа вопросов, паузу, ошибки, победу/поражение, звук и перезапуск. Сборку упаковать отдельно, связав с commit и версией движка.

## Другие платформы

Общий проект является отправной точкой. Профили macOS/Web/Android/iOS пока не добавлены и сборки не проверены. Web требует отдельной оценки рендерера и браузерных ограничений; мобильные устройства — интерфейса и ввода. Не менять Forward+ автоматически ради экспорта. macOS и iOS — разные цели.

## Контент и генераторы

Код отделяет `voice_id` от `audio`. При замене аудио сохранить ID вопроса, обновить путь `audio`, импортировать ресурс и проверить цикл, паузу и остановку. Карточки и слайды уже готовы; генераторы могут перезаписать их. Не запускать `Recovery/` и `Source/tools/` без чтения кода и отдельной задачи. У ряда исторических скриптов сохранены абсолютные пути прежней среды.

В Git сохраняются код, данные, готовые ассеты, исходные модели, `.import` и `.uid`. Кэш `.godot/`, EXE/PCK и локальные credentials исключены. При импорте другой версией движка следить за изменениями `.import` и не смешивать их молча с игровой правкой.


## Автосборки и диалог с Дмитрием

Windows pipeline: `.github/workflows/windows.yml`, Godot **4.5.1**, экспорт на `ubuntu-24.04`, затем smoke-проверка EXE на `windows-2022`. Официальные редактор и export templates проверяются по закреплённым SHA-256. Выбор 4.5.1 сохраняет исходную версию проекта; не подменять её установленным в чате 4.6.3.

Исходники выгружаются только на Linux. Исторические References содержат имя с двоеточием, недопустимое для Git checkout на Windows даже при sparse checkout. Материалы остаются в Git без переименования. На Windows передаётся только экспортированная игра, метаданные и CI-скрипты; checkout репозитория там не выполняется. Промежуточный Actions artifact хранится 1 день. Полный clone для сохранности проверялся в Linux.

Триггер — изменения `Source/`, `tools/ci/`, конфигурации сборки или launcher в `work/**`; доступен ручной workflow_dispatch, в том числе для main. Простой merge принятой задачи в main не создаёт ещё одну preview и не возвращает её в ожидание приёмки. Документация сама по себе не вызывает тяжёлую сборку. Запуск через подключённый GitHub App проверять фактически: не считать коммит доказательством старта workflow.

Порядок: unit-проверки CI → `tools/ci/check_content.py` (216 ID и текущие медиа) → импорт → editor `--qa` (все 6 маркеров, контроль ошибок и тайм-аутов) → экспорт Windows → запуск экспортированного EXE `--headless -- --qa` → ZIP → публикация Pre-release. В release-шаблонах GDScript assert выключены, поэтому EXE-проверка является smoke-тестом загрузки/выполнения, а проверки утверждений выполняются редактором на Linux до экспорта. Нет GUI-проверки, оценки звука человеком и проверки GPU.

`verify_recovery.py` остаётся отдельной исторической проверкой baseline; намеренные будущие изменения не должны автоматически ломать CI по старым хешам. Сам baseline-манифест не переписывать под исправления.

Секретов вручную добавлять не требуется: workflow использует временный `GITHUB_TOKEN` с `contents: write`, переданный как GH_TOKEN только шагам публикации/статуса. Эти операции требуют разрешённых GitHub Actions и прав workflow в репозитории. Не печатать токен и не сохранять его в коде или артефактах.

Каждая попытка выпускает уникальный тег `test-<run_id>-<attempt>-<sha8>`, не перезаписывая прежнюю сборку и не делая preview Latest. Вложения: ZIP, build.json, SHA256SUMS.txt. В ZIP: EXE со встроенным PCK, CMD совместимости, BUILD-INFO.json и ПРОВЕРКА.txt. Логи импорта/QA/экспорта сохраняются отдельным Actions artifact на 7 дней; тестовые релизы автоматически не удаляются. Состав и хеш ZIP после загрузки сверяются с GitHub.

`.github/build-target.json` определяет целевую платформу и короткий список ручных проверок. Сейчас реализована только Windows. При другой платформе pipeline прекращает Windows-экспорт; прежде чем обещать Web/macOS/iOS/Android, реализовать и проверить их отдельный процесс. Не менять платформу, рендерер или механику скрытно.

Агент работает с одним `work/<задача>` и одним STATUS. После готовности выдаёт ссылку на release и 2–4 продуктовых пункта проверки. После завершения workflow обновляет блок `ci-preview` в STATUS своей ветки: точный source commit, журнал, ссылка и «ждёт проверки Дмитрия». Если ветка уже ушла вперёд, workflow сохраняет результат в release/run и не затирает новый статус. Ошибочная попытка записывается как ошибка; не считать её готовой сборкой. После ручной приёмки агент сохраняет отзыв и переносит принятую работу в main. Одна лишь автозапись не является пользовательской приёмкой.

### Стабильный выпуск без повторной сборки

Только после явного согласия пользователя на выпуск и проверки конкретной preview заполнить `.github/release-request.json` в main:

```json
{
  "version": "v1.0.1",
  "preview_tag": "test-<реальный run_id>-<attempt>-<sha8>",
  "source_commit": "<полный commit из build.json>",
  "accepted_by": "Дмитрий: <фактическое подтверждение и дата>"
}
```

Это пример, не выполненная приёмка. Сейчас version=null, стабильный выпуск не запрошен. Commit запускает `.github/workflows/release.yml`. Он сравнивает Source и launcher с принятой версией, скачивает и проверяет тот же preview ZIP и публикует стабильный release с ACCEPTANCE.json. Повторная компиляция не производится: пользователь получает тот же файл, который проверял. Если игровой код/ассеты изменились, выпуск блокируется до новой preview и приёмки. Существующий тег не перезаписывается; новая версия требует нового номера. Историю request хранит Git.

В первом CI на 4.5.1 все шесть групп QA прошли, но при завершении отмечены ObjectDB leak warning и «4 resources still in use at exit». Детектор разрешает только точную форму этого teardown-сообщения после всех шести маркеров и exit code 0; сохраняет её отдельно в журнале, build.json и release notes. Другие ERROR, ошибки скриптов, пропущенные маркеры и тайм-ауты блокируют публикацию. Это не утверждение отсутствия утечек и не замена ручной проверки.
