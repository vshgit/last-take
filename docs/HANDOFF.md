# Продолжение из нового чата

## Отправная точка

Репозиторий: https://github.com/vshgit/last-take, рабочая ветка восстановления — `main`. Это восстановленная файловая база 1.0.0, а не вся покоммитная история создания игры: до переноса работа велась в одном длинном чате.

1. Открыть репозиторий, проверить remote HEAD, ветку и `git status`.
2. Прочитать `AGENTS.md`, `README.md`, `docs/STATUS.md`, `docs/DECISIONS.md`, `docs/DESIGN.md`, `docs/DEVELOPMENT.md`, `docs/RECOVERY.md`.
3. Работать с `Source/project.godot`. Не создавать другой проект с нуля.
4. Если исходники недоступны в GitHub, найти сохранённый файл `LastTake-Recovered-Source-2026-11-09.zip`. Исходный резервный архив с EXE называется `LastTake-Windows-v1.0.zip`; checkpoint 1.0 сам по себе неполный.
5. Для понимания вопросной базы смотреть `Source/content.json` и `References/LastTake_All_216_Questions(2).docx`. Другие DOCX — исторические варианты, не применять их автоматически поверх банка.

## Что важно не перепутать

- В банке 216 вопросов, в одном сеансе 21. Правила одной ошибки устарели: сейчас 3 общие скрытые жизни.
- 0.10 / v10 — более ранняя версия. Файл с названием v10 не новее 1.0 / v1.
- DEMO-аудио не является оригинальными репликами актёров; требование об оригинале A13 остаётся невыполненным.
- Картинки, модели, звуки и исходники нужно сохранять, а не заменять из предположений о происхождении.
- Сборка Windows, проверка Linux и поддержка macOS/Web/телефона — разные факты.
- Полный текст первого чата не сохранён. Если важного решения нет в документах, обозначить пробел, не выдумывать.
- Лицензии отложены; не добавлять MIT и не удалять существующие сведения об источниках самовольно.

## Начальное сообщение агенту

> Работаем с Last Take: https://github.com/vshgit/last-take. Сначала прочитай AGENTS.md и документы docs/STATUS.md, DECISIONS.md, DESIGN.md, DEVELOPMENT.md, HANDOFF.md и RECOVERY.md, проверь текущий commit. Продолжай существующий Godot-проект Source/project.godot. Не переписывай игру. Моя следующая задача: [описание]. Разделяй действующие решения, фактическую реализацию и предположения. Сохраняй игровые файлы и обновляй статус после работы.

## Порядок завершения следующей задачи

Проверить затронутое поведение, обновить статус и новые решения, сохранить изменения в Git, проверить фактический remote SHA и дать ссылку на commit. При блокере доставки сохранить отдельную резервную копию и прямо сообщить, какая часть осталась локальной.

## Простой цикл следующих задач
Текущая задача и очередь — в docs/STATUS.md. Отдельный трекер Issues не обязателен. Для игровых изменений достаточно одной рабочей ветки и последующего переноса принятого результата в main; документацию можно обновлять непосредственно в main, если игровые файлы не затрагиваются. Не создавать инфраструктуру ради самой инфраструктуры.

Дмитрий общается в чате и проверяет игру. Вопросы ему — о желаемом результате; техническое решение выбирает агент. При внешнем техническом блокере предложить позвать Варю и кратко объяснить, что от неё требуется.

Перед работой определить целевую платформу. Сейчас основная — Windows. Задача по браузеру требует браузерной проверки и ссылки на тестовую версию после настройки размещения; EXE для неё не является обязательным результатом. То же правило относится к macOS, iOS и Android. Смена основной платформы фиксируется отдельно. Для документации сборка не нужна.

При возобновлении сначала найти ожидающую приёмки сборку/URL и последний отзыв. Не считать задачу принятой по одним автоматическим тестам. Windows-автосборки описаны в docs/DEVELOPMENT.md; их фактический последний результат читать в STATUS и GitHub Actions. Браузерный порт ещё не реализован.

Для новой Windows-задачи: work/<задача> → commit/push → проверить Windows preview → ссылка на тестовый release → дождаться отзыва Дмитрия → сохранить отзыв и приёмку → merge. Агент сам выполняет Git-операции. Для стабильного выпуска после отдельного согласия оформить release-request на main; детали и проверки происхождения ZIP — в DEVELOPMENT. Последний автоматический результат сохраняется в STATUS самой рабочей ветки; перед выводами читать и STATUS в main, и STATUS активной ветки. Новый чат не должен требовать повторной загрузки исходников или EXE.
